# agent-api: External decision interface: per-player game observation, every legal option for every decision, JSON protocol for outside agents

GOAL: an external program (for example a Python harness around an LLM, or a search or learning agent) can play any seat in a game: at each decision the engine sends it what that player can see of the game plus the complete list of legal choices, and accepts its answer. Today agents are in-process Rust `Agent`s (decision.rs: `Agent::decide(&mut self, &Game, PlayerId, &Decision) -> Answer`; see agents.rs RandomAgent, testing.rs ScriptedAgent, mtg-sim). Read decision.rs, casting.rs (legal actions), game.rs `ask()`, and how RandomAgent enumerates options, before designing.

REQUIREMENTS
1. Observation (what the deciding player can see), serializable to JSON: turn number, active player, phase/step, priority holder; per player: life, poison and other player counters, mana pool, hand (contents for the viewer and for cards the viewer is allowed to see, such as revealed cards or a hand they may look at; a count otherwise), library count (plus any known top cards), graveyard, exile (face-down exiled cards hidden unless the viewer may look at them), command zone, designations (monarch, initiative, city's blessing, day/night, ring tempts, speed...), lands played this turn. Battlefield objects with ids and their CURRENT characteristics after layers: name, mana cost, colors, types and subtypes, power/toughness, loyalty/defense, counters, tapped/flipped/phased/face-down state, damage marked, summoning sickness, attachments, controller and owner, keywords, rules text (Oracle text plus granted abilities where available), combat status (attacking whom, blocking what, blocked or not). Stack: each object with source, controller, text, chosen modes, X, and targets. Hidden information must follow the rules: library order, opponents' hands, and face-down objects' identities (CR 708) are never shown to a player who can't see them. Also provide an omniscient view (all information) for logging and debugging.
2. Decisions: map EVERY `Decision` variant to a serializable request carrying an explicit list of legal options, each with a stable index, a short readable description (card names, ability text, target names) and structured fields (object ids, player ids, costs), plus the answer shape it expects (pick one; pick between min and max; order a list; choose a number in a range; divide an amount among items; yes/no). For priority, list EVERY legal action: each castable spell (with each alternative cost or casting permission that applies), each activatable ability, each land play, each special action, and pass. The list must be complete and exact: every listed option is accepted, and the engine accepts nothing that isn't listed. Reuse the engine's own legality code; don't build a second rules implementation.
3. Answers: a JSON answer (by option index, or index list, number, etc.) is converted to an `Answer` and validated. On an invalid answer, return an error message to the agent and ask again (configurable retry count), then fall back to the engine's default.
4. Event feed: with each request, the events since that player's previous decision (spells cast, abilities activated, zone changes, damage, life changes, combat), described without leaking hidden information, so a model can follow the game.
5. Transport and embedding:
   (a) `ExternalAgent: Agent` speaking newline-delimited JSON over a child process's stdin/stdout (one request per line, one answer per line), and
   (b) a pull-style Rust API for embedding the engine in a server: run the game on its own thread with channel-backed agents, and expose something like `session.next() -> Option<Request>` / `session.answer(seat, answer)` so a caller can drive one or more seats step by step. (Optional: a TCP or stdio server mode in mtg-sim that hosts a game for remote clients.)
   (c) mtg-sim CLI: per-seat agent selection, e.g. `--agent 0=random --agent 1=cmd:'python3 examples/random_client.py'`, working with --deck / --random-decks.
6. Documentation and example: docs/AGENT_PROTOCOL.md (message schemas with real examples taken from a game, answer formats, hidden-information rules, error handling, versioning) and a minimal dependency-free Python client in examples/ that plays by choosing random legal options. Mention it in README.md.

PLACEMENT: prefer a new crate `crates/mtg-api` (observation and request types, serde, conversions, ExternalAgent, session API) that mtg-sim depends on, so engine core files change as little as possible (other agents edit them in parallel). Build the observation as separate view structs constructed from `&Game`, not by deriving Serialize across engine internals. If the engine lacks something you need (for example a way to enumerate legal options for some decision, or to tell what a player may see), add a small focused hook in the engine.

TESTS (crates/mtg-api/tests or crates/mtg-engine/tests): JSON round trip for every Decision variant; completeness and exactness, i.e. across many game states (TestGame setups plus a short loop of random-deck games) every listed option is accepted and nothing unlisted is; hidden information (an opponent's hand cards, library order and face-down identities never appear in a player's observation, while the controller of a face-down permanent does see it, CR 708.5); invalid answers get an error and a re-ask; a complete game played through the JSON protocol with a child process (the example client, or an in-test child process) finishing without errors; the pull session API driving a full game. Cite CR rules with cr!() where a test exercises them (e.g. hidden information 400.2, 708.5; priority 117).

DONE when an external process can play complete games in any seat through documented JSON, using only what its player is allowed to see and choosing from complete lists of legal options.
