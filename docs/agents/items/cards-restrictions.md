# cards-restrictions: Restriction grammar: activation, casting, combat, targeting and rules prohibitions — 401 texts / 402 cards (345 unlocked alone)

SCOPE: 401 unsupported ability texts (401 on paper cards) blocking 402 paper cards; 345 of those become fully supported when this item alone is done (the others also have a text owned by another item). The full list, with the failing piece found by compiler probes, ships as items/cards-restrictions.texts.tsv (columns: cards blocked, normalized text, example card, piece kind, failing piece). Normalized text = reminder text removed, the card's own name as ~, numbers as N.

GOAL: Activation restrictions ("Activate only if you've discarded a card this turn", "only during the declare blockers step", "only once", "no more than three times each turn", "Only your opponents may activate this ability and only as a sorcery", "Any player may activate this ability but only as a sorcery", "Activate only if enchanted land is untapped"), casting restrictions ("Cast ~ only if a creature died this turn", "can't be countered" for the next spell, "you can't cast more than one spell each turn"), combat restrictions and requirements with conditions ("~ can't block unless ...", "can't block or be blocked by non-Spirit creatures", "No more than one creature can attack ~ each combat", "Creatures named X can't attack you", "Other creatures that player controls can't block this turn"), targeting restrictions ("can't be the target of abilities your opponents control"), and rules prohibitions ("Players can't draw cards or gain life", "Creature cards in graveyards can't enter the battlefield", "Creatures you control can't have -1/-1 counters put on them").

APPROACH: 1. Activation restrictions: parse a list of restriction clauses joined by "and"/"but" into ActivationTiming + conditions + who-may-activate + max-per-turn; conditions via the condition grammar (history conditions from cards-history-conditions).
2. Prohibitions: SUBJECT (players/permanents/cards filter) + "can't" + action (draw, gain life, enter the battlefield, have counters put on them, be the target of [source filter], attack [whom], block [whom]) + duration → `Restriction` variants; add the missing actions generically.
3. Combat restrictions/requirements with "unless" and "if able" use cards-conditions-state-unless conditions.

PARSER FILES INVOLVED: oracle/costs.rs (split_activation_restrictions — owned by cards-costs-activated; add a hook), oracle/statics.rs (self restrictions), patterns/restrictions_cast.rs, restrictions_combat.rs, restrictions_timing.rs, restrictions_untap.rs, must_target.rs, r505_cast_during_main_phase.rs, conditional_uncounterable.rs

FILES THIS ITEM OWNS: new oracle/patterns/restriction_grammar.rs and activation_restrictions.rs; may edit restrictions_*.rs, must_target.rs, conditional_uncounterable.rs

ENGINE CAPABILITIES: Restriction AST is large; likely missing: "can't enter the battlefield" for cards in a zone, "can't have counters put on them", per-attacked-object attack limits ("no more than one creature can attack ~"), restrictions on who may activate (opponents only).

COMMON RULES FOR CARD ITEMS:
- Generalize. Implement each construct as grammar (subject / verb / object phrase / qualifiers composed from phrases.rs, the value and condition parsers and the Builder's referent tracking), never one pattern per card wording; a fix should also cover wordings that aren't in the list. Unit-test the grammar on several real wordings.
- Faithfulness first. The parser must not accept text the engine doesn't implement exactly (an Oracle round-trip check audits every compiled card). For each family add TestGame tests with real cards that assert the in-game outcome (crates/mtg-engine/tests/cards/ or tests/cr/, citing cr!() for rules exercised and ruling!() for Scryfall rulings exercised).
- A text can contain a second failing construct owned by another item. Fix it when it is small; otherwise leave it and list it under remaining gaps with the owning item.
- One-offs. If a text's construct is genuinely unique (no other card shares it) and compiling it would be hacky, don't force it: once cards-manual-defs has landed, give it a hand-written definition in src/cards/ with a test; before that, list it as a manual candidate.
- Shared core files (oracle/effects.rs, phrases.rs, statics.rs, triggers.rs, costs.rs, ability.rs, eval.rs, resolve.rs) are edited by several items in parallel: keep edits there small (hooks, new enum variants handled everywhere), put grammar in this item's own pattern files, and merge origin often.
- Measure before and after: `cargo run --release -q -p mtg-tools -- card-coverage` and the baseline filters above. Report per family: texts fixed, texts remaining (each with a reason). Run `cargo run --release -p mtg-sim -- --random-decks --games 300` before finishing to catch panics in newly supported cards.
- DONE when about 90% or more of this item's texts compile with faithful, tested behaviour and every remaining text is listed with a reason (engine gap, belongs to item X, manual candidate).
